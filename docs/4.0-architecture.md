# Satisfy 4.0 architecture

Status: in development on `FivePaths/satisfy`, branch `4.x`. The interface stays Satisfy's: the same `satis.json`, output URLs, webhook paths, admin UI and environment variables. What changes is how builds run and what serves the catalogue.

## Roles

| Role | Runs | Serves |
|---|---|---|
| web | nginx and php-fpm | The output directory as static files; PHP only for `/admin`, `/login` and `/webhook/*` |
| worker | `bin/console satisfy:worker` | Nothing. Takes queued build requests and runs Satis |

The image (`docker/Dockerfile`) runs both by default, so `docker run` works as it did in 3.x; its entrypoint's first argument is `all`, `web`, `worker` or `rebuild`. nginx and php-fpm start without `COMPOSER_AUTH` in every role, and running the worker in a container of its own also keeps a mounted `auth.json` away from them. On every start the entrypoint compiles the configuration afresh, and copies the image's front controller and assets into `public/` in case it is a volume an older image filled.

## The build queue

- A directory, `SATISFY_QUEUE_DIR` (default `var/queue`). Each request is one JSON file, written to a temporary name and renamed into place: `full.json` for a full build, `repo-<sha1 of the URL>.json` for one repository. Two requests for the same repository before the worker reaches them are one file, so they make one build.
- The worker claims everything pending by moving it into `processing/`, runs one Satis build for the lot, and deletes the claimed files. A full build covers everything; otherwise it passes each URL as `--repository-url`, with `--repository-strict`.
- On start the worker moves anything left in `processing/` back into the queue, so a worker killed mid-build loses nothing.
- Builds run under the `build` lock. `satisfy:rebuild` takes the same lock and still builds in the calling process, so a script can run a check, a build and a cleanup in order.
- The worker writes the last build's output to `var/log/build.log`, and one JSON line per build (scope, exit code, seconds) to its own output.

## What asks for a build

- A webhook dispatches `BuildEvent`. The queue's listener enqueues the repository and marks the event queued, and the webhook answers 202 with `queued`. A listener that stops the event's propagation first prevents the build, and the webhook answers 200 with `skipped`.
- The admin UI's build page queues a full build by POST, and shows the queue and the last build's log.

## Events

These are the points plugins attach to.

| Event | Dispatched | Used for |
|---|---|---|
| `BuildEvent` | A webhook or the UI asks for a build | Inspecting or refusing the request |
| `BuildStartingEvent` | The worker is about to run Satis | Checks that can cancel the build |
| `BuildFinishedEvent` | Satis has exited | Work after a build: cleaning up `p2/` after a full build, confirming a publish |

Planned with the plugin increment:

| Event | Dispatched | Used for |
|---|---|---|
| `WebhookReceivedEvent` | Any verified delivery, with provider, event kind and ref | Acting on tag pushes |
| `RepositoryAddingEvent` | Before a webhook auto-adds a repository; can be refused | Deciding what may be registered |

## Plugins

- A plugin is a Symfony bundle. While plugins mature they live in this repository under `plugins/<Name>/`, each with its own namespace. `config/bundles.php` enables those listed in `SATISFY_PLUGINS` (comma-separated), so enabling one needs no image rebuild.
- The first two are services FivePaths runs beside Satisfy today, to be ported:
  - **authz.** Per-token access to the catalogue, with per-package grants whose dependency closure is computed from `p2/`. nginx calls its endpoint through `auth_request`, so the image's nginx configuration gets an `auth_request` slot that is on when the plugin is. Its verification endpoint stays a plain PHP script that does not boot the kernel, because Composer calls it hundreds of times per update. Its command-line tool becomes `authz:*` console commands, and its web UI becomes admin pages.
  - **hookgate.** A registration gate on `RepositoryAddingEvent`: a repository is added only if some ref has a `composer.json` declaring an allowed type. On `WebhookReceivedEvent` it adds a tagged package to `require`. The rules that are particular to one catalogue are configuration.
- Either may later be proposed for upstream's main branch as it stands.
